# 05 – UI

The UI has one job: let a reviewer make a good decision quickly, and let an organiser make a second one deliberately. It should feel like a staff tool, not a marketing site. Familiarity with Ari is a feature.

## Principles

1. **The queue is the home.** A reviewer signs in and lands on work, not a dashboard.
2. **One screen, one decision.** The review page contains everything needed to decide. No wizard in stage 1, no modal chain, no "next step" unless a required field genuinely needs one.
3. **Show the work, not the tool.** Evidence is primary; chrome is quiet. The review screen is dense but calm.
4. **The default action is obvious.** Approve is primary and shows the hours it credits. Request changes and reject are secondary but always visible.
5. **Speed without carelessness.** Warnings are visible, blocking failures are explained, and approval with an unacknowledged warning takes one extra confirmation.
6. **Familiarity over novelty.** Keep Ari's layout, vocabulary, shortcuts and status colours. A reviewer should not have to relearn where the commit list is.
7. **No dead ends.** Every empty state says what to do next. Every error says whether to retry, wait, or ask an admin.

## The queue

```text
Queue                                             [Start reviewing]
[All] [Design] [Build]   [Ready to approve] [Needs a look]   Search…

┌──────────────────────────────────────────────────────────────────────┐
│ Project                         Maker      Waiting   Checks   Claim  │
├──────────────────────────────────────────────────────────────────────┤
│ PCB · Line follower             Ada        2h        ●●●      free   │
│  design · week 1 · 8.5h                                            │
├──────────────────────────────────────────────────────────────────────┤
│ CAD · Desk lamp                 Grace      5h        ●●○      you    │
│  build · week 7 · 3.2h                                             │
├──────────────────────────────────────────────────────────────────────┤
│ Displays · Weather clock        Linus      1d        ●○○      Sam    │
│  design · week 4 · 14.1h                                           │
└──────────────────────────────────────────────────────────────────────┘
```

Columns:

- **Project** – title, theme, phase, week, hours. The title is the link. A small theme dot/colour helps scanning.
- **Maker** – display name only (PII rule). Avatar if available.
- **Waiting** – relative time since ingest; the exact date on hover.
- **Checks** – three dots: pass / warn / block. A warning count is more useful than a single amber dot; show `2` if there are two.
- **Claim** – "free", "you", or the reviewer's name. A stale claim is free.
- **Priority** – a star/pin at the left if the maker requested priority (if the programme uses it).
- **Update** – a small "v2" badge for a resubmission.

Filters:

- phase (design/build), theme, track, claim state, check state.
- "Ready to approve" is a dynamic filter over the latest checks: no warns, no blocks, required checks done, no current claim by someone else.
- "Needs a look" is the inverse: warns, errors, acknowledgements needed, or a manual flag.
- Sort: oldest first (default), newest, longest evidence, shortest. Priority pins first.
- Search: title, maker display name, external id. FTS5 if available; otherwise a capped `LIKE`.

The "Start reviewing" button opens the first unclaimed ship in the current filter. If the current filter is empty, it says so and offers to clear the filter. It does not jump to a random ship.

### Queue states

- **Loading:** skeleton rows, not a spinner over a blank page.
- **Empty:** "Queue zero. Nice." with a link to reviewed or the other track.
- **Error:** "Could not load the queue" + retry + a request id.
- **New work:** an SSE event refetches; a subtle "3 new" chip appears instead of reordering under the reviewer's cursor. Reordering a table while someone is clicking is a bug.

The left column is evidence; the right rail is the decision. This is Ari's shape, simplified for stage 1.

### Top bar

- Back to queue (with the current filter preserved).
- Position: "Submission 3 of 14" in the current filter. `j`/`k` or arrows move.
- Weekly goal meter (optional; programme setting).
- Shortcuts (`?`), finish session, user menu.
- Stage badge: `Stage 1`, `Stage 2 · held`, `Stage 2 · fraud`.

### Header

- Cover image, with a lightbox. If absent, a theme plate, not a broken image.
- Title, description (fold after ~3 lines; expand).
- Meta: theme, phase, week, received time, update badge.
- Maker: display name + avatar. No email/Slack at stage 1.
- Links: repo, demo, copy buttons, keyboard hints (`r`, `v`).
- If the project is a resubmission: "Update · v2" and a "What changed" link that scrolls to the diff.
- If the maker is flagged: a red callout. If identity is unverified: a warning callout. These are stage 2/PII-gated.

### Preflight strip

The most important addition to Ari. It answers "is anything wrong?" before the reviewer reads a single journal entry.

- Grouped by source: repo, evidence, demo, identity, history.
- Each line: status icon, key fact, short detail.
- Green: pass. Amber: warn. Red: block. Grey: skipped/error.
- A count badge in the collapsed header: `2 warnings`.
- Expanding shows the individual checks, timestamps, and raw data (file list, commit authors, Hackatime projects).
- A "Re-run" action per group, with a spinner and a toast. It does not block the page.
- If a check is still running: "Checking…" with the group name; approve is disabled only if the policy says the check is required.

The strip is not a tab. It stays visible above the evidence.

### Evidence tabs

Keep Ari's dock idea but simplify it to tabs on desktop and a segmented control on mobile.

- **Overview** – README rendered, project description, BOM summary, key facts.
- **Files** – tree/list with file-kind badges (PCB source, BOM, CAD, firmware, model). Link to the forge. Show which required/recommended kinds were found.
- **Commits** – list with author, date, message, additions/deletions, coding time; filter by author; highlight mismatched authors.
- **Devlog** – journal entries with time, text, images, clip links; sortable by date; "wordless" badge.
- **Clips** – grid/list of timelapse clips with thumbnail, covered time, runtime, Hackatime project; click to open.
- **History** – prior reviews, prior versions, resubmission diff, disputes (read-only if Half Life owns them).

The default tab is chosen by what is most useful:

- stage 1: Overview if README exists, otherwise Devlog.
- stage 2: Overview, with the held decision panel above it.

Tabs remember the last-used tab per reviewer per stage. The URL carries `?tab=commits` so a link is shareable.

### Right rail

Order, top to bottom:

1. **Logged time** – total, source breakdown, coverage, adjustments. A small bar shows journal vs Hackatime. Clicking a source opens the adjustment editor.
2. **Funding** (design only) – BOM total, tier grant, shortfall, partial-funding/declined callouts. Stage 1 sees it; stage 2 can change the tier if policy allows.
3. **Checklist** – only if configured for this stage/track. Required items gate approval.
4. **Custom fields** – only if configured. Required fields gate approval.
5. **Note to maker** – optional on approve by default; required for changes/reject. Snippet picker (`/`), character count, plain text/Markdown preview.
6. **Internal note** – optional at stage 1 by default; required for overrides at stage 2. Never shown to the maker.
7. **Decision buttons** – sticky at the bottom of the rail.

The rail scrolls independently. On narrow screens it stacks under the evidence, and the decision buttons become a sticky bottom bar.

### Decision buttons

- **Approve · 8.5h** – primary green. Shows the hours it will credit. Disabled with a tooltip when a required field, check, or claim blocks it.
- **Request changes** – neutral/orange. Opens the note focused; sends the maker back.
- **Reject** – red. Opens the note focused; explains "no credit".
- **Stage 2:** **Confirm**, **Override**, **Send back**. Override opens a decision picker + reason.

A compact confirm popover for approve:

```text
Approve Line follower?
8.5h will be credited. Note: "Approved! …"
[Approve]  [Cancel]
```

`Enter` confirms; `Esc` cancels. The popover shows whether the decision will be held for stage 2. If it will, the button says "Approve · held for stage 2" and the popover explains why.

### Stage 1 focus mode

A toggle (or automatic when the ship is clean) hides the rail's optional sections and the evidence tabs that have no content, leaving:

- preflight;
- the default evidence;
- hours;
- note;
- decision buttons.

This is the "just decide" mode. It is not a separate route; it is a UI state remembered per reviewer. It must never hide a blocking warning or a required field.

## Stage 2 screen

Same shell, different rail and an extra panel above the evidence.

```text
┌ Held for stage 2 ─────────────────────────────────────────────────────┐
│ Stage 1 approved · Ada · 2h ago · 8.5h                                │
│ "Nice board, clean BOM. The firmware is tidy."                       │
│ Hold reason: approved hours over 8h                                  │
├ Fraud ────────────────────────────────────────────────────────────────┤
│ ✓ Passed · score 8/10 · "Repo and identity look consistent."         │
├───────────────────────────────────────────────────────────────────────┤
│ [Confirm approval]  [Override…]  [Send back to stage 1]              │
└───────────────────────────────────────────────────────────────────────┘
```

- The held decision panel is always first. It shows stage, reviewer, time, decision, note, hours, and the hold reason.
- The fraud panel shows status, verdict, score and summary. If pending, it says "Fraud check running"; confirm is disabled. If error, "Fraud unavailable" with retry/override.
- The organiser sees the same evidence and checks; the first-pass note is quoted, not editable.
- Confirm requires no note unless policy says so. Override requires a reason and a new decision. Send back requires a reason.
- If the organiser made the stage 1 decision, confirm is disabled with "Your own decision needs another organiser."
- A "Compare with stage 1" link scrolls to the stage 1 note and hours; it does not open a diff view of the whole project.

### Stage 2 queue

Columns: Project, Stage 1 decision, Reviewer, Held for, Age, Fraud, Claim. Default sort: oldest hold first. Filters: decision kind, hold reason, fraud status, reviewer.

A "Fraud pending" chip is not a blocker for reading; it is a blocker for confirming.

## States and feedback

| State | UI |
| --- | --- |
| Loading queue | Skeleton rows |
| Loading review | Skeleton header + preflight + tabs; no layout shift |
| Claim held by another | Read-only banner with "Open read-only" / "Take over" if stale |
| Claim lost | Banner "Another reviewer claimed this"; decision disabled; reload |
| Stale version | Banner "This ship was updated while you were reviewing"; reload |
| Checks running | Preflight lines with spinners; approve disabled only if required |
| Check error | Grey line "Could not check: …"; acknowledgement if it blocks |
| Decision submitting | Button spinner; inputs disabled; no double submit |
| Decision succeeded | Toast "Approved · next up in 2s" with "Stay"; auto-advance |
| Decision failed | Inline error with code and retry; draft preserved |
| Outbound failed | Admin banner; reviewer sees "Decision recorded, delivery pending" |
| Fraud pending | Stage 2 panel says so; confirm disabled |
| Fraud error | Stage 2 panel says so; retry/override with reason |
| Empty queue | "Queue zero. Nice." + link to reviewed |
| Offline | "You are offline"; queue remains readable; writes disabled |

## Keyboard

Keep Ari's shortcuts. Add a few stage 1 conveniences.

| Key | Action |
| --- | --- |
| `j` / `↓` | Next submission |
| `k` / `↑` | Previous submission |
| `a` / `Ctrl/Cmd+Enter` | Approve (opens confirm) |
| `c` / `Ctrl/Cmd+Shift+Enter` | Request changes |
| `x` / `Ctrl/Cmd+Backspace` | Reject |
| `n` | Focus note to maker |
| `i` | Focus internal note |
| `/` | Snippet picker |
| `r` | Open repo |
| `v` | Open demo |
| `f` | Flag / escalate (stage 2 or admin) |
| `?` | Shortcuts dialog |
| `Esc` | Close dialog / cancel confirm |
| `1`…`7` | Evidence tabs |
| `Space` | Open selected evidence row (when a list has focus) |

Rules:

- Shortcuts do not fire while typing in an input, textarea or select.
- `a` opens the confirm popover, not an immediate write. `Enter` confirms. This is two keystrokes and still fast; it prevents an accidental approval when a reviewer's hand slips.
- If the programme enables one-click approval, it is a policy setting and the button says so.
- The shortcuts dialog is generated from the same registry as the handlers, so it cannot drift.
- Every shortcut has a visible label in a tooltip or menu.

## Data loading and performance

- The queue response includes rows only; no evidence.
- The review bundle is one request. It includes:
  - submission + project + maker (redacted by role);
  - latest check results + summary;
  - journal entries (capped), commits (capped), clips (capped), BOM, repo snapshot summary;
  - prior reviews and previous version summary;
  - policy and viewer permissions;
  - claim state.
- The browser prefetches the next three bundles on idle. It does not prefetch media.
- Images lazy-load with `loading="lazy"` and `referrerpolicy="no-referrer"`.
- README is rendered from Markdown on the server (Go) or client? Render on the client with a small, safe Markdown renderer, or sanitise on the server. To avoid an XSS surface, render Markdown to sanitised HTML on the server and return HTML in the bundle. If the bundle is large, return raw Markdown and render with a strict renderer that escapes HTML. The plan prefers server-side sanitised HTML for consistency, capped at 200 KB.
- Evidence arrays are capped: 200 journals, 200 commits, 100 files, 50 clips. If there are more, the bundle says "showing 200 of 340" with a paginated endpoint.
- The page is usable before images load. No layout shift: reserve aspect ratios.
- Performance budget: cached bundle < 300 ms TTI on a laptop; uncached < 1 s on a good connection. If it is slower, profile the SQL and the payload size before adding a spinner.

## Visual system

- **Density:** staff tool. 13-14px body, 12px metadata, 16-20px headings. Tables are compact but not cramped.
- **Colour:** a quiet neutral background, one accent for primary actions, semantic green/amber/red for status. Never rely on colour alone: every status has an icon or label.
- **Typography:** one sans family; tabular figures for hours, dates, counts.
- **Spacing:** 4px scale; consistent panel padding; no nested cards.
- **Borders:** 1px, low contrast; use spacing before boxes.
- **Motion:** minimal. Auto-advance uses a short fade; respect `prefers-reduced-motion`.
- **Empty states:** one sentence + one action, not an illustration.
- **No marketing hero, no giant headings, no gradients** in the staff console.

The scaffold's warm paper theme is a starting point for a standalone app, but the review console should be closer to Ari's neutral staff UI: white/near-white surfaces, dark text, a single accent. The Half Life brand can appear in the wordmark and the programme chip, not in the data surfaces.

## Accessibility

- Every action is reachable by keyboard; focus is visible.
- The confirm popover traps focus and restores it on close.
- Tables have proper headers and captions; status cells have text labels.
- Colour contrast at least WCAG AA for text and controls.
- No time-limited interactions except the claim TTL, which is extended by activity and explained.
- `prefers-reduced-motion` disables auto-advance animation and smooth scrolling.
- Screen-reader announcements for decision success/failure and queue updates; do not announce every SSE event.
- Form errors are linked to fields with `aria-describedby`.
- The review screen works at 360px wide; the rail stacks and the decision bar sticks to the bottom.

## Familiarity checklist

Before calling the UI "familiar", a reviewer should be able to answer yes to all of these:

- I can find the queue and start reviewing without being told.
- I can see the project, maker, repo, demo and hours without opening another tab.
- I can find the commits, devlog, clips, README and files where they were in Ari.
- I can claim, finish a session and move to the next ship the same way.
- I can approve, request changes and reject with the same words and roughly the same keys.
- I can see the note to maker and the internal note in the same rail.
- I can tell whether a decision is final or going to a 2nd pass before I confirm it.
- I can see why a ship is in stage 2 and who decided at stage 1.
- I can see what changed on a resubmission without re-reading everything.
- I can tell the difference between "the check failed" and "the check could not run".

If any answer is no, the UI is not done, regardless of how it looks.

## What not to build

- A dashboard-first landing page. The queue is the landing page for reviewers.
- A multi-step wizard in stage 1.
- A modal for the whole review.
- A separate "evidence" app or tab that reloads.
- Infinite scroll on the queue. Pagination/keyset is more predictable.
- A chat or comments feature in v1. Notes and audit are enough.
- A dark mode before the light mode is right. (Add it later if reviewers ask; tokens make it cheap.)
- A mobile-native app. Responsive web is enough.
- Gamified streaks or points for reviewers. A weekly goal meter is the limit.
